# Event Hubs

- Event Hubs is a big data streaming platform and event ingestion service
- Event Hubs is basically a managed Kafka implementation
- It can receive millions of events per second
- Events are **not** deleted after being read, they are kept for the configured **retention period** and can be re-read (stream, not queue)
- Delivery is **at-least-once**, consumers **pull** events at their own pace
- Supports AMQP, HTTPS and the **Kafka protocol** (Standard tier and above, no code change needed for Kafka clients)

## Event Hubs Components

- Namespace:
    - Top level container with a unique FQDN `<name>.servicebus.windows.net`
    - Tier, capacity (TU/PU/CU), network rules and geo-DR are configured at namespace level
    - A namespace can host multiple event hubs (an event hub is the equivalent of a Kafka topic)
- Event Producers:
    - Components that are generating the events
    - Events can be generated by anyone with a client or with a HTTP client
    - Events producers only need to utilize simple API connections
    - A **partition key** can be supplied so related events always land in the same partition (keeps ordering per key)
- Partitions:
    - Partitions represent single event streams
    - We can think of them as a single queue
    - They guaratee the order of the messages
    - Partitions have limited availability, there is no way to make a partition HA
    - Better to spread messages across partitions to improve availability => the order of the messages will not be guaranteed
    - We can have max 32 partition on a single Event Hubs deployment (up to 100 on Premium, 1024 on Dedicated)
    - Partition count is set at creation time and **cannot be changed** later (except on Premium/Dedicated)
    - The number of partitions should be >= the number of concurrent consumers in a consumer group
- Consumer Group:
    - It is a logical group of receivers, belonging to the same application
    - It is a separate **view** (state, position, offset) of the same event stream
    - Example:
        - Receivers for processing telemetry
        - Receivers for storing telemetry
    - Event receiving is done via AMQP protocol
    - Recommended: only one active receiver per partition per consumer group
    - Basic tier: 1 consumer group ($Default), Standard: 20, Dedicated: 1000
- Offset & Checkpointing:
    - **Offset / sequence number** identifies the position of an event inside a partition
    - Consumers **checkpoint** their position into a **checkpoint store** (Azure Blob Storage), so processing can resume after a restart or a rebalance

## Retention

- Basic: 1 day
- Standard: up to 7 days
- Premium / Dedicated: up to 90 days

## Event Hubs Capture

- Automatically writes the incoming stream to **Blob Storage** or **Azure Data Lake Storage** in **Avro** format
- Configured with a time window (min 1 minute) or size window (min 10 MB), whichever happens first
- No code needed and it does not affect throughput; ideal for cheap long term archiving and batch processing
- Not available in the Basic tier

## Scaling

- **Auto-inflate** (Standard): automatically scales TUs up as load increases (it does not scale back down automatically)
- Premium uses **Processing Units (PU)** and Dedicated uses **Capacity Units (CU)** for isolated capacity

## Tiers

- **Basic**: 1 consumer group, no Capture, no Kafka, no Schema Registry
- **Standard**: 20 consumer groups, Capture, Kafka, Schema Registry, auto-inflate
- **Premium**: PU based, resource isolation, Private Endpoints, CMK, more partitions, longer retention
- **Dedicated**: single tenant cluster (CU based), highest scale, Capture included, BYOK
- Max event (message) size: 1 MB

## Availability

- SLA:
    - Basic and Standard tiers: 99.95%
    - Dedicated: 99.99%
- Availability Zone support in regions that offer AZs (Standard and above)
- **Geo-DR**: pairs namespaces behind an **alias**, replicates **metadata only**, failover is manual
- **Geo-replication** (Premium/Dedicated): replicates metadata **and** event data

## Security

- **Microsoft Entra ID** with managed identities (recommended). Built-in roles:
    - Azure Event Hubs Data Owner
    - Azure Event Hubs Data Sender
    - Azure Event Hubs Data Receiver
- **SAS** policies with Send / Listen / Manage rights
- IP firewall rules, Service Endpoints, Private Endpoints (Premium/Dedicated)
- Encrypted at rest by default, customer-managed keys (CMK) on Premium/Dedicated

## Throughput Units (TU)

- Throughput is measured in Throughput Units
- 1 TU = 
    - Ingress: 1 MB / sec or 1000 events / sec
    - Egress: 2 MB / sec or 4096 events / sec
- TU as prepurchased, billed by the hour
- Standard tier: up to 20 TU per namespace (more on request), exceeding the limit results in throttling

## Pricing

- It is based on:
    - Tier
    - Ingress
    - Throughput Units (TU)
- Capture is billed separately (included in Dedicated)

## When to Choose Event Hubs

- High volume telemetry, logs, clickstream, IoT ingestion and real time analytics pipelines
- Multiple independent consumers need to read the **same** stream (consumer groups) or replay past events
- Typical downstream services: Stream Analytics, Azure Functions, Databricks, Synapse, Storage (Capture)
- Choose **Service Bus** for enterprise messaging with transactions / FIFO / dead-lettering, **Event Grid** for discrete reactive events pushed to handlers
- **IoT Hub** is preferred for device management and bi-directional device communication
